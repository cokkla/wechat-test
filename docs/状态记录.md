## 2026-09-18（更晚期）

### 排查记录 - WiFi 下访问下载链接 502，与代码/服务无关
- **现象**：手机用流量（走真正外部公网路径）访问 `PUBLIC_BASE_URL` 下的下载链接能正常下载；手机连自家 WiFi（内网访问自己的公网域名/IP）访问同一链接返回 `502`。
- **原因**：NAT Hairpin（NAT 环回/U 型转发）不支持。
  - 手机用流量：请求从运营商网络出发，走公网到路由器公网口，再转发进内网，是标准的"外部 → 内部"路径，路由器处理正常。
  - 手机连 WiFi：手机和跑 `server.py` 的机器在同一局域网，但访问的是"自己家的公网域名/IP"，请求需要先从内网绕出去、经运营商网络绕回路由器公网口，再转发回内网——这种"自己人访问自己"的环回路径，很多消费级路由器（尤其国产入门/中端型号）不支持做这层 NAT 转换，直接失败或返回错误页，表现为 502。
- **结论**：跟本项目的 `server.py`、`config.py` 配置、企业微信接口调用都无关，纯粹是路由器硬件/固件限制。真实的外部访问（包括微信服务器的回调请求）不受影响，可以正常联调测试。
- 若后续要在同一 WiFi 下测试下载链接，可选方案（暂未实施）：改用局域网内网 IP + 端口直接访问、给路由器刷支持 Hairpin NAT 的固件（如 OpenWrt）、或换一台支持该功能的路由器。

## 2026-09-17

### 完成 - 游标持久化（修复重复回复问题）
- **问题**：每次重启服务后，`_cursor_store` 被清空，导致 `sync_msg` 从头拉取所有历史消息（包括已回复过的），然后每条 `origin == 3` 的消息都触发回复，很快触发微信客服 **95001: send msg count limit** 错误（48小时内最多回复5条）。
- **解决方案**：将游标持久化到 `cursors.json` 文件：
  - `_load_cursors()`: 启动时从文件加载已保存的游标位置。
  - `_save_cursors()`: 每次 `sync_msg` 更新游标后立即保存到文件。
  - 在 `if __name__ == "__main__"` 入口调用 `_load_cursors()`。
- 更新 `.gitignore` 新增 `cursors.json`（游标文件不提交到版本库）。
- 补充 `test_server.py` 测试用例（新增 4 个，总计 27 个全部通过）：
  - `TestSyncMsg.test_saves_cursor_after_each_page`: 验证每次分页后都调用 `_save_cursors()`。
