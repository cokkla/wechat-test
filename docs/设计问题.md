# 设计问题

## 文件上传 → 处理 → 回传结果流程

### 背景
现有上传流程是"上传完立刻回一句文本"，不存在处理阶段。但实际场景需要支持"上传 → 处理 → 处理完再推送结果"，这引入了多个新的隐藏风险。

身份绑定的前半段（上传时）没问题：token 在客户发触发词时直接从当次消息取 `external_userid + open_kfid`，签名封装进 token，上传接口读出来用于回推。这一步不会把 A 的身份和 B 的身份串起来。

但处理阶段是新增的，代码完全没有为它设计任何东西。下面列出的不是"A 的信息传给了 B"的直接文体，而是更隐蔽的几种风险。

---

### 风险清单

#### 1. 缺少独立的任务标识（job_id）

**现状问题**
- 目前 token 只编码了 `external_userid + open_kfid`，这两个是"发给谁"的路由信息
- 不是"这是哪一次上传"的任务标识
- 当客户短时间内上传两次文件（如先传一张错的，再传一张对的），处理阶段无法区分

**失效场景（异步处理）**
- 处理需要排队、调外部服务或耗时较久
- 你怎么知道"处理完的这个结果对应的是哪一次上传"？
- 如果处理逻辑用"这个客户最近一次上传的文件"来配对结果，在并发或客户连续操作时会张冠李戴
- 不是传错客户，而是传错了那次上传对应的文件

**需要的改动**
- 每次上传单独生成一个 `job_id`
- 从上传落盘、处理、到最终推送结果，全程用 `job_id` 显式传递
- 不能靠"猜最近一次"这种脆弱推断

---

#### 2. 任务映射需要持久化，不能只在内存里

**现状问题**
- `_used_upload_tokens` 是内存里的 `set()`（server.py:38）
- 服务重启就清空
- 处理阶段如果耗时较长（几分钟到几小时），期间服务重启一次，映射关系就彻底丢了

**需要的改动**
- 落盘存储（如 `jobs.json` 或简单的 SQLite）
- 至少要包含以下字段：
  - `job_id`：任务唯一标识
  - `external_userid`：客户身份
  - `open_kfid`：客服号
  - 上传时的文件路径
  - 状态：待处理 / 处理中 / 已完成 / 已推送

---

#### 3. 48 小时会话窗口的限制

**现状问题**
- `kf/send_msg` 有硬限制：客户 48 小时内没有再发消息，客服号就没法主动推消息给他
- 参考 `docs/发送消息.md:5`
- 如果处理耗时超过这个窗口，"处理完想推给客户"这一步会直接失败

**失效后果**
- 不是身份错了，是压根发不出去
- 现在 `upload_file()` 里 `send_text_msg` 失败只是打印日志就完事（server.py:369）
- 处理结果实际上丢了

**需要的改动**
- 失败需要被记录和感知
- 至少要能被人看到 / 告警
- 不能打印日志后静默丢失

---

#### 4. 多租户支持（未来可能性）

**当前不需要（单租户），但值得记一笔**

现状：`CORP_ID / SECRET` 是写死在环境变量里的单租户配置

未来风险：
- 如果这套服务要同时服务多个企业微信主体
- A 企业签发的 token 在 B 企业的上下文里被误用
- 会导致用错的 `access_token` 调用，处理结果被推给了错误租户下的客服号

改动方案：
- token 里加一个 `corp_id` 字段
- 处理和推送时显式校验 `corp_id` 匹配

---

#### 5. 上传文件的完整性校验（可选）

**建议做法**

如果处理阶段涉及把文件传给别的服务 / 队列，中间经过网络或存储：
- 在落盘时计算文件 hash（如 SHA256）
- 存进任务记录里
- 处理完成后比对，避免文件被意外替换或损坏

这也是身份 / 数据一致性的一部分：保证"处理的确实是这个客户传的这个文件"

---

### 需要补充的身份 / 任务标识

1. **job_id**
   - 每次上传单独生成
   - 贯穿处理全流程
   - 不依赖"最近一次"这种脆弱推断

2. **持久化的任务状态记录**
   - `job_id → external_userid + open_kfid + 文件路径 + 状态`
   - 扛得住服务重启

3. **corp_id**（多租户场景下）
   - token 里加一个字段
   - 处理和推送时显式校验

4. **文件内容 hash**（可选，完整性校验）

5. **48 小时窗口过期的失败处理**
   - 至少要能被人看到 / 告警
   - 而不是打印日志后静默丢失

---

### 关键设计决策待确认

**当前场景的处理模式是什么？**

这决定了 `job_id` 落盘方案要不要引入队列 / 后台线程：

- **同步**：上传接口里直接调用处理逻辑再返回结果
- **异步**：丢进队列，处理完再回调推送

## 开发指导大纲

这部分从状态记录中提取已实现的功能约束和设计模式，作为后续开发参考。

### 一、消息同步与游标管理

**已实现**：游标持久化（cursors.json），避免重启后重复回复历史消息。

**待考虑**：
- **掉线后消息断层**：如果服务离线期间客户发送了消息，服务恢复后 `sync_msg` 能拉到的历史消息有多久的窗口？企业微信是否有数据过期丢弃？建议测试一下：离线 1 小时 / 1 天后重启，看是否能拉回消息，以此明确掉线补偿的策略（是否需要告知用户消息可能漏了，还是能完全补齐）。
- **异常恢复**：cursors.json 文件损坏 / 被误删后的容错。目前应该是自动重置，但需明确是否会导致消息重复回复、是否需要告警。

---

### 二、文件管理与大小限制

**已实现**：
- 企业微信原生上传限制（image/voice 2MB、video 10MB、file 20MB）绕开方案：客户发触发词 → 服务推送独立 HTTP 上传链接
- 上传文件大小上限配置（`UPLOAD_MAX_SIZE`，默认 200MB，Flask `MAX_CONTENT_LENGTH` 限制）
- 文件名清理（中文保留、路径穿越防护、重名时间戳避重）

**文件推送限制**：文件超 20MB 后，`media/upload` 无法上传到微信素材库，改为推送下载链接（link 消息），链接指向服务端公开下载路由。

**待考虑**：
- **下载链接安全**（[状态记录.md:71](../docs/状态记录.md#L71)）：当前 `GET /files/<filename>` 完全公开无鉴权，文件链接泄露可被任意转发下载。上线前需评估：是否加签名 token / 过期时间、是否检查来源、是否记录下载日志。
- **文件保存期限**（30 天）：需定期清理过期文件的后台任务，避免磁盘爆满。
- **每用户配额**（5GB）：需在上传时检查用户已用空间，拒绝超配的上传。这需要建立 user → total_usage 的映射表（待持久化方案）。

---

### 三、身份隔离与租户管理

**当前**：单租户单企业（`CORP_ID` / `SECRET` 写死在环境变量），body 里通过 `external_userid` 区分客户。

**待考虑**：
- **个人用户隔离**（租户 = 个人用户级别）：
  - 同一服务可能服务多个企业主体（未来），或同一企业下多个业务独立维护（near future）
  - 用户的上传文件、处理任务、配额统计都需要按 `external_userid` 隔离，不能混
  - 建议在 job 表、user_quota 表里显式加 `corp_id` 和 `external_userid` 作为联合主键，而不是依赖全局配置
- **权限与签名**：上传 token 和下载链接签名时需同时绑定身份信息，防止 A 用户的 token 被 B 用户挪用

---

### 四、配置与密钥管理

**已有**：
- `.env`：`WECHAT_TOKEN`、`WECHAT_ENCODING_AES_KEY`、`CorpTD`、`Secret`、`URL`
- `config.py`：功能开关与参数（上传触发词、文件路径、超时配置等）

**建议规范**：
- `.env`：密钥与外部服务凭证（`WECHAT_TOKEN`、`WECHAT_ENCODING_AES_KEY`、`CorpTD`、`Secret`、回调 URL）
- `config.py`：业务参数与功能开关（触发词、文件目录、超时、大小限制）
- 后续如引入数据库、加服务间通信，相应的 DSN / 服务端口也应归入 `.env`

---

### 五、文件完整性与安全校验

**当前**：上传文件后保存落盘，无校验。

**待考虑**：
- 如果处理阶段涉及把文件传给别的系统（如 PDF 处理服务），建议在落盘时计算 SHA256，记入 job 表；处理完后比对 hash，确保文件未被篡改或丢失。
- 文件类型白名单（当前无），建议允许哪些格式、拒绝哪些类型（如 `.exe`），防止误上传恶意文件。

---

### 六、错误处理与可观测性

**当前**：错误主要以日志打印 + 用户文本回复呈现。

**待考虑**：
- **48 小时窗口过期**：如果推送结果失败（window closed / customer not exist），不能仅打日志，需标记为"失败状态"，便于人工或告警系统感知。可考虑在 job 表里加 status_detail 字段，记录最后一次推送的失败原因。
- **重试机制**：某些失败可重试（如网络抖动），某些不行（如 window closed）。建议预留重试次数字段，区分可重试和不可重试的错误类型。

---

### 七、异步处理与任务队列

**当前场景**：所有操作同步完成（上传保存 → 立刻回复、推送文件 → 立刻确认）。

**如需扩展异步**（如处理阶段改为外部服务调用）：
- 上传接口里不再直接处理文件，而是返回 job_id + 稍后通知客户的承诺
- 后台任务从 job 表读待处理任务、调用外部服务、处理完成后调用回推接口
- 建议显式设计 job 表的状态转移（pending → processing → completed / failed），避免隐式依赖内存状态

---

### 八、测试覆盖范围

**已有**：单元测试覆盖签名、解密、上传、下载、触发词等。

**建议补充**：
- 集成测试（真实企业微信客户端与后端交互，验证 UI 流程）
- 压力测试（并发上传、配额校验在高并发下是否正确）
- 长期测试（游标持久化、文件过期清理、磁盘使用是否稳定）
